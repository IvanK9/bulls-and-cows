# DESIGN.md

Документация содержит обоснование архитектурных решений, анализ сложности Big O для функций, демонстрацию принципов Clean Code на конкретных участках кода и чек-лист поведения приложения.

---

## 1. Структуры данных и алгоритмы

### Структуры данных

- **История попыток и состояние игры (Array):** История ходов представлена иммутабельным массивом объектов. Применение структуры данных `Array` в функциональном стиле позволяет использовать встроенные методы перебора и декларативно отрисовывать UI. Каждая новая попытка добавляется через оператор spread (`[...history, newEntry]`), что полностью исключает мутации.
- **Мемоизация (Record/Объект):** Для кэширования результатов рекурсии используется стандартный JS-объект в качестве хэш-таблицы. Поиск и запись значений по строковому ключу вида `"length-base"` выполняются за константное время O(1).

### Описание ключевых алгоритмов

- **`evaluateGuess`:** Алгоритм работает без использования императивных циклов `for/while`. Строка попытки игрока преобразуется в массив символов `[...guess]`. Подсчет Быков выполняется методом `.filter()`, который оставляет только те символы, чей индекс и значение строго совпадают с секретной строкой. Подсчет Коров выполняется аналогично, но условие фильтра проверяет, что символ присутствует в секрете (`.includes()`), но его текущий индекс не совпадает с позицией в секрете. Итогом является объект с длинами получившихся отфильтрованных массивов.
- **`countPossibleSecrets`:** Алгоритм рассчитывает количество уникальных комбинаций секретного числа. Реализован на основе чистой рекурсии. Базовым случаем (выходом из рекурсии) является уменьшение длины числа до 0, при котором функция возвращает 1. В остальных случаях функция рекурсивно умножает текущее основание системы счисления на вызов самой себя с уменьшенными на единицу параметрами (`base * countPossibleSecrets(length - 1, base - 1)`). Для предотвращения избыточных вычислений перед каждым шагом происходит проверка наличия результата в объекте-кэше.

## 2. Сложность алгоритмов (Big O)

Ниже приведена оценка сложности для ключевых функций. Параметр N обозначает длину секретного числа (`length`), а параметр B — основание системы счисления (`base`).

- **`generateSecret`:**
  - _Временная сложность:_ O(B \log B) — квазилинейная. Основное время тратится на перемешивание исходного массива всех доступных символов системы счисления методом `.sort()`. Современные движки используют алгоритмы сортировки со сложностью O(B \log B).
  - _Пространственная сложность:_ O(B) — линейная, требуется для хранения массива всех доступных символов перед срезом нужной длины.
- **`evaluateGuess`:**
  - _Временная сложность:_ O(N) — линейная для фиксированных игровых ограничений. Происходит двукратный проход по массиву символов длины N с помощью `.filter()`. Поиск `.includes()` внутри фильтра выполняется за O(N) в худшем случае, что для малых N \le 6 дает фиксированно малое количество операций.
  - _Пространственная сложность:_ O(N) — линейная, память выделяется под новые отфильтрованные массивы символов Быков и Коров.
- **`isValidGuess`:**
  - _Временная сложность:_ O(N) — линейная. Метод `.every()` совершает N итераций для проверки валидности каждого символа. Создание коллекции `new Set()` для проверки уникальности также требует ровно один проход по строке длиной $N$.
  - _Пространственная сложность:_ O(N) — линейная, выделяется память под хранение уникальных символов в структуре `Set`.
- **`countPossibleSecrets`:**
  - _Временная сложность:_ O(1) — константная при повторных вызовах. Благодаря мемоизации, функция вычисляет значение для конкретного режима игры всего один раз, а при последующих обращениях мгновенно достает результат из кэша за O(1).
  - _Пространственная сложность:_ O(length \times base) — пропорциональна количеству уникальных комбинаций настроек, сохраняемых в объекте-кэше.

## 3. Принципы чистого кода (Clean Code)

- **Принцип DRY (Don't Repeat Yourself):** Выделение доступных символов для систем счисления вынесено в утилитарную функцию `getAllowedChars(base)` в файле `src/core/game.ts`. Это исключило дублирование кода в функциях валидации и генерации секрета.
- **Single Responsibility Principle (Принцип единой ответственности):** Четкое разделение бизнес-логики и UI. Файл `src/core/game.ts` содержит исключительно чистые функции расчета математики игры и ничего не знает о DOM. Файл `src/ui/render.ts` отвечает только за генерацию элементов интерфейса и подписку на события.
- **Принцип содержательных имен (Meaningful Names):** Все переменные и функции имеют прозрачные имена, отражающие их суть. Вместо абстрактных `a`, `b`, `fn` используются `secretCode`, `historyState`, `elapsedSeconds`, `createDigitValidator`, что делает код самодокументируемым.
- **Строгая типизация без приведения типов (Type Safety):** В файле `src/ui/render.ts` при работе с DOM-элементами полностью отсутствует использование небезопасного оператора `as` (Type Assertion). Безопасное сужение типов и проверка элементов на существование реализованы через оператор `instanceof` (например, `baseSel instanceof HTMLSelectElement`).

## 4. Чек-лист поведения приложения

- [x] Настройки длины (2–6) и системы счисления (bin/oct/dec/hex) доступны до старта и блокируются после.
- [x] При выборе двоичной системы недоступны (задизейблены или скрыты) все длины, кроме 2.
- [x] Поле ввода не принимает символы, недопустимые для выбранной системы счисления.
- [x] Ввод цифр hex в верхнем регистре (A–F) принимается наравне со строчными.
- [x] После каждой попытки появляется новая запись в истории с числом bulls/cows.
- [x] Повторный ввод уже использованной попытки не приводит к задвоению записи в истории (как именно обработать повтор — на ваше усмотрение, главное без ошибок).
- [x] При угадывании секретного числа игра корректно завершается, засчитывается число попыток и время.
- [x] Результат попадает в таблицу рекордов, рекорды переживают перезагрузку страницы.
- [x] «Новая игра» возвращает к экрану настроек без перезагрузки страницы.
